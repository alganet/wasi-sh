The shell below is a dev server, and it is a shell script — the whole thing is at the bottom of this page. It parks in read <&3 between requests, costing no CPU; a request posted from here wakes it in under a millisecond, and it answers with an ordinary outbound verb.

This is the one direction postMessage cannot go. A live session is a single synchronous _start() frame, so the worker's event loop never turns while the shell runs: a message posted into it is not slow, it is not delivered. A request travels through shared memory the guest reads at its blocking point instead.

inbound — session.post() → the parked loop

— writes the shell's own filesystem, so the next GET /notes sees it. One worker, one VFS, nothing to keep in sync.

requestBufferSize is the grant: without it
/dev/hostreq is EPERM, the redirection fails and the
loop refuses to start — a different thing from "nothing has arrived yet", and
the script can tell them apart. Capabilities are injected, never ambient; the
outbound half works the same way, with no host meaning every open
of /dev/host is EPERM.
